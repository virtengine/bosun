## Symptom -> proof -> code path -> fix or blocker

### 1. UI-owned workflow engines were re-owning interrupted-run recovery on startup
- Symptom:
  - real workflow runs kept getting reclassified as interrupted and resumed while the UI server was crash-restarting
  - the old log pattern showed repeated `ui-server` startup lines interleaved with repeated `Resuming ... interrupted run(s)` bursts
- Proof:
  - `server/ui-server.mjs` started a workflow worker proxy and then explicitly called `resumeInterruptedRuns()`
  - `server/workflow-engine-worker.mjs` also auto-called `resumeInterruptedRuns()` on startup
  - the UI worker/request paths did not disable interrupted-run detection, so UI-owned engines could touch the same run store as the monitor
- Code path:
  - `server/ui-server.mjs:2071+`
  - `server/ui-server.mjs:3818+`
  - `server/workflow-engine-worker.mjs:257+`
- Fix:
  - UI-owned workflow engine proxies and UI in-process fallback now disable interrupted-run detection on startup
  - worker startup resume is now gated by `resumeInterruptedRunsOnStart !== false`
  - regression coverage updated in `tests/workflow-worker-recovery-regression.test.mjs`
